# R005 需求分析

## 1. 需求定性

- 类型：Bug
- 定性说明：这是现有前端节点管理页的交互缺陷，不是新需求，也不是单纯体验优化。问题会直接导致节点信息无法连续输入，属于功能性故障。

## 2. 涉及文件列表（预估）

- `frontend/src/pages/Nodes.tsx`
  - 节点新增入口 `openAddModal(...)`
  - 节点编辑弹窗 `Modal` 与受控表单 `editForm`
- `frontend/src/components/Modal.tsx`
  - 弹窗打开后的自动聚焦逻辑
  - `useEffect` 当前依赖包含 `onClose`，父组件每次重新渲染时可能重复执行聚焦
- `frontend/src/components/PromptDialog.tsx`
  - 新增节点使用的通用表单弹窗组件，需要确认修复后是否存在同类失焦或回归
- `frontend/src/pages/MonitorShares.tsx`
  - 也存在 `Modal + 内联 onClose` 的写法，若本次按通用组件修复，需要一并回归验证

## 3. 依赖检查

- 前端范围：仅涉及 React 19 + TypeScript 前端逻辑，当前排查看不到后端 API、数据库结构、Go 服务端逻辑的改动需求。
- 关键依赖：
  - `react` / `react-dom`
  - 自研通用组件 `Modal`
  - 节点页本地状态 `editForm`
- 已确认现象触发链：
  - `frontend/src/pages/Nodes.tsx` 中编辑节点弹窗的 `onClose={() => (!saving ? setEditingNode(null) : null)}` 是内联函数。
  - 编辑表单任一输入框 `onChange` 会触发 `setEditForm(...)`，导致 `Nodes` 组件重新渲染。
  - `frontend/src/components/Modal.tsx` 的聚焦 `useEffect` 依赖 `[open, onClose]`，因此每次重渲染都会再次执行，把焦点重新聚到首个可聚焦元素。
  - 这会表现为输入一个字符后焦点跳走，尤其在编辑第二个及之后的字段时最明显。
- 结论：
  - 这是前端弹窗聚焦逻辑和节点页写法组合导致的 Bug。
  - `@dnd-kit`、节点接口、数据结构、健康检查逻辑与本问题无直接关系。

## 4. 实现方案概述

1. 先在 `Nodes.tsx` 明确复现路径，重点验证“编辑节点”弹窗中的 `Base URL`、`API Key`、`权重` 等字段是否每次输入后跳回首字段。
2. 调整 `Modal.tsx` 的自动聚焦实现，使其只在弹窗真正打开时执行一次，而不是在父组件每次重渲染时重复执行。
3. 为 `Escape` 关闭、遮罩关闭等行为保留最新 `onClose`，避免修复聚焦后引入闭包过期问题；必要时用 `ref` 持有最新回调。
4. 复查 `Nodes.tsx` 与其他 `Modal` 调用点，尽量避免在高频重渲染场景继续传递会不断变化的内联关闭函数，减少同类问题再次出现。
5. 验证新增节点、编辑节点、其他表单弹窗的输入连续性和关闭行为，最后执行 `cd frontend && npm run build`。

## 5. 风险点

- 如果只在 `Nodes.tsx` 局部规避，而不修正 `Modal.tsx` 的聚焦触发时机，其他页面仍可能复现同类问题。
- 如果只修改 `Modal.tsx` 依赖数组，可能导致 `Escape` 或遮罩关闭拿到旧的 `onClose` 回调，需要同时处理回调引用更新。
- `PromptDialog.tsx` 当前也依赖 `Modal`，通用修复后要确认新增节点弹窗、确认框等对话框的初始聚焦和回焦行为没有退化。
- 聚焦逻辑属于通用交互基础设施，改动虽小，但影响面比节点页单文件更广，需要做最少量的弹窗回归。

## 6. 建议

- 结论：接受
- 原因：
  - 该问题直接阻断节点信息录入，影响核心管理功能。
  - 目前根因已经较明确，修复范围集中在前端弹窗与节点页交互层，实施成本较低。
  - 不涉及后端协议和数据库变更，回归成本可控。

## 7. 预估优先级

- 优先级：1
- 说明：节点管理是核心后台页面，输入框失焦会导致新增/编辑节点基本不可用，属于应优先处理的高影响 Bug。
